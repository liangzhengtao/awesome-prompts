## 安全审计 / Security Audit

### 1. OWASP Top 10 安全审查

```
你是一位资深安全工程师，请对以下代码进行 OWASP Top 10 安全审查。

语言：[LANGUAGE]
框架：[FRAMEWORK]
代码：
```[CODE]```

请按以下格式输出：
1. 🔴 严重漏洞（Critical）
2. 🟠 高危漏洞（High）
3. 🟡 中危漏洞（Medium）
4. 🔵 低危漏洞（Low）

每个问题请包含：
- 问题描述
- 风险等级
- 攻击场景
- 修复建议（含代码示例）
```

### 2. SQL 注入与 XSS 检测

```
审查以下代码中的 SQL 注入、XSS 和 CSRF 漏洞。

上下文：[CONTEXT_DESCRIPTION]
代码：
```[CODE]```

对每个发现的漏洞：
1. 标注具体行号
2. 解释攻击向量
3. 提供安全的替代实现
4. 推荐使用的安全库/函数
```

### 3. 认证与授权审查

```
作为安全审计专家，审查以下认证/授权相关代码的正确性。

代码用途：[PURPOSE]
代码：
```[CODE]```

重点检查：
- 密码存储方式（哈希算法、盐值处理）
- Token 生成与验证逻辑
- 会话管理安全性
- 权限边界是否完整
- 是否存在越权访问风险

输出格式：逐项列出问题并给出修复代码。
```

### 4. 依赖安全检查

```
检查以下项目依赖文件中的已知安全漏洞。

请：
1. 标记有已知 CVE 的依赖
2. 说明漏洞影响范围

4. 如果没有安全替代，推荐替代库

## 性能审查 / Performance Review

### 5. 时间复杂度分析

```
分析以下代码的时间复杂度和空间复杂度，并找出性能瓶颈。

语言：[LANGUAGE]
代码：
```[CODE]```

请提供：
1. 当前复杂度分析（时间 & 空间）
2. 性能瓶颈所在
3. 优化方案（附优化后代码）
4. 优化后的复杂度对比
5. 适用场景说明（何时该用原方案，何时该优化）
```

### 6. 数据库查询优化

```
审查以下数据库查询的性能问题。

数据库：[DATABASE]（如 MySQL/PostgreSQL/MongoDB）
查询代码：
```[QUERY_CODE]```

数据规模：约 [ROW_COUNT] 行

请分析：
1. 是否存在 N+1 查询问题
2. 是否缺少必要的索引
3. 查询是否可以简化或合并
4. 是否需要分页处理
5. 缓存策略建议

输出优化后的查询和推荐的索引创建语句。
```

### 7. 内存泄漏检测

```
审查以下代码中可能存在的内存泄漏或资源泄漏问题。

语言/运行时：[LANGUAGE]
代码：
```[CODE]```

重点检查：
- 未关闭的文件句柄、数据库连接、网络连接
- 事件监听器未移除
- 闭包导致的引用无法释放
- 循环引用
- 定时器未清理

对每个问题给出修复代码。
```

### 8. 并发性能审查

```
审查以下并发/异步代码的性能和正确性。

语言：[LANGUAGE]
代码：
```[CODE]```

请分析：
1. 竞态条件（Race Conditions）
2. 死锁风险
3. 线程池/连接池配置是否合理
4. 锁的粒度是否合适
5. 是否存在不必要的同步操作

## 可读性检查 / Readability Check

### 9. 代码可读性评分

```
请对以下代码进行可读性评估，满分 10 分。

语言：[LANGUAGE]
代码：
```[CODE]```

评估维度：
- 命名规范（变量、函数、类名是否清晰表达意图）
- 函数长度（是否需要拆分）
- 注释质量（是否过多/过少/过时）
- 代码结构（缩进、空行、组织方式）
- 一致性（风格是否统一）

输出：
1. 各维度评分
2. 具体改进建议（附重构后代码）
3. 整体可读性评分
```

### 10. 命名优化

```
审查以下代码中的命名，提出改进建议。

代码：
```[CODE]```

语言：[LANGUAGE]
项目上下文：[PROJECT_CONTEXT]

对每个不佳的命名：
1. 指出原始命名
2. 说明为何不佳
3. 推荐 2-3 个更好的替代名称
4. 标注命名遵循/违反的规范
```

### 11. 代码味道检测

```
识别以下代码中的"代码味道"（Code Smells）。

代码：
```[CODE]```

语言：[LANGUAGE]

检查以下常见代码味道：
- 重复代码（Duplicated Code）
- 过长函数（Long Method）
- 过大的类（Large Class）
- 过长参数列表（Long Parameter List）

- 数据泥团（Data Clumps）

```

## 架构评审 / Architecture Review

### 12. SOLID 原则审查

```
根据 SOLID 原则审查以下代码的设计。

代码：
```[CODE]```

语言：[LANGUAGE]
项目描述：[PROJECT_DESCRIPTION]

逐项检查：
- S（单一职责）：每个类是否只做一件事
- O（开闭原则）：是否对扩展开放、对修改关闭
- L（里氏替换）：子类是否可以替换父类
- I（接口隔离）：接口是否过于庞大
- D（依赖倒置）：是否依赖抽象而非具体

对违反原则的部分，给出重构方案。
```

2. 数据所有权是否清晰
3. API 边界是否合理
4. 是否存在分布式单体的迹象
5. 通信方式是否合适（同步 vs 异步）

## 综合审查 / Comprehensive Review

### 15. 全面代码审查（Pull Request 风格）

```
请对以下代码变更进行全面审查，模拟 Pull Request Review。

变更类型：[CHANGE_TYPE]（如新功能/Bug 修复/重构）
关联需求：[REQUIREMENT]
变更文件：
```[CHANGED_CODE]```

审查清单：
✅ 功能正确性 - 代码是否正确实现了需求
✅ 边界条件 - 是否处理了边界/异常情况
✅ 安全性 - 是否存在安全隐患
✅ 性能 - 是否存在性能问题
✅ 可读性 - 代码是否易于理解
✅ 测试 - 测试覆盖是否充分
✅ 向后兼容 - 是否破坏现有 API

输出格式：
- 🟢 Approve（无需修改）
- 🟡 Comment（建议修改，非阻塞）
- 🔴 Request Changes（必须修改）
```

## 💡 使用技巧 / Tips

1. **提供上下文**：始终告诉 AI 代码的用途、规模和技术栈，审查结果会更精准
2. **分层审查**：对大型代码库，先架构后细节，不要一次审查过多代码
3. **结合 CI**：将审查 prompt 的输出与 CI 工具结合，实现自动化审查
4. **迭代优化**：根据第一次审查结果追问细节，往往能得到更深入的分析

## ⚠️ 常见错误 / Common Mistakes

- ❌ 不提供代码上下文，导致 AI 无法判断业务逻辑是否正确
- ❌ 一次提交过多代码，超出 AI 的有效处理范围
- ❌ 只关注语法，忽略安全和性能维度
- ❌ 盲目接受所有建议，不结合实际情况取舍
